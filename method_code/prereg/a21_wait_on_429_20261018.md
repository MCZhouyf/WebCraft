# A21 author-authorized waiting on HTTP 429

Rule formed on 2026-10-18 after the author instructed that HTTP 429 must
not terminate execution. Six development episodes and partial prefixes of
20 and 11 decisions have already been observed. No formal A21 episode has
run. Original registrations and results are retained without modification.

Only A21 transport changes. With the explicit wait-on-429 option, a 429
from either an action request or a canary is retried in place indefinitely.
Waits are 60, 120, 240, then at most 300 seconds for subsequent consecutive
429s on that client; an HTTP Retry-After value (seconds or HTTP date) can
extend that wait. A shared cooldown pauses all workers, and the shared
20-second HTTP start spacing still applies. No credential is rotated to
avoid cooldown. Successful action generation resets the local streak;
a successful small canary does not reset an existing action-request streak.
Only successful action responses consume the existing 40-decision budget.
HTTP attempts, failures, and waiting are logged separately with no secrets.

Model mismatch, malformed or incorrect canary content, authorization errors,
input/hash divergence, and exhausted existing non-429 error retries retain
their protected stop behavior. Waiting does not clear any safety latch.

An owned background controller may run the existing registered stages in
order: development, formal K, then formal controls and offline analysis.
Each scientific gate is read from the unchanged gate script; no failed gate
is bypassed and no task is selected using model outcomes. If the registered
shortened variant is needed but not yet implemented, report
NEEDS_REGISTERED_SHORTENING instead of claiming completion or launching
controls. A result above the gate's upper bound also stops advancement.

Completed episodes are retained. Any partial prefix is verified offline
before reuse. Prompts, facts, model, decoding, action budgets, scoring, and
statistics are unchanged. The controller keeps credentials memory-only,
uses the existing server.lock protocol, writes an inspectable live status,
and does not touch WebCraft, GPU services, or unrelated processes.
