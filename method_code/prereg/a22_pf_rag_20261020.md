## Candidate identity and opening probe rule

Use the existing compiled relation convention: mine groups by node_type;
craft_grid/smelt group by method and output. Candidate payload identity is
canonical JSON of method, params, input options, output, count, requirements
and layout slots, excluding confidence and provenance. Distinct provenance
copies of the same payload count once for conflict scoring. A conflict pair
is an unordered pair of unequal payloads in the same relation. No conflict
catalogue, expected version, gold mechanism family or feasibility is consulted.

Identifier references are the union of explicit compiled input choices,
output, requirements, node_type, fuel, and explicit workstation identifiers
actually present in the candidate/provenance assertion. Do not guess station
names from an action type, consult an item catalogue, or parse version strings.
Only namespace stripping of minecraft: is permitted for identifiers.

Score identifier x by the number of remaining conflict pairs in whose two
reference sets x occurs on exactly one side. Greedily select maximum score,
ties lexicographically by identifier. Call public check_name once per selected
identifier. Each consumes one action and its actual public semantic cost.
After an absent result remove affected candidates and recompute scores over
survivors; never probe the same identifier twice. Stop at B, budget exhaustion,
or zero maximum score. This phase occurs once, after reader/compiler and
before planning; no later opening probes or version reports.

The sole fallback is global: only if every development evidence bundle has
an empty discriminating-identifier set, use the output identifiers of conflict
candidates, scored by number of conflict pairs referencing the output, ties
lexicographic. Freeze fallback_enabled in the selected config and log it for
every episode. No per-task fallback. No conflicting candidates means no probes
even with fallback. No alternatives to this fallback are authorized.

## Filtering and revision generalization

Absent means the public response contains resolvable=false. True is evidence
of existence only, not of recipe/drop correctness. Missing/nonboolean values
are indeterminate and produce no filtering. Hard-remove every candidate
referencing an observed-absent identifier, across all mechanisms. Retain its
public provenance in an audit trail, not in the planner's active operator set.

Revision identity is (source_site,page_title,revid), so unrelated sites' numeric
revision IDs cannot collide. Mark a revision suspect iff at least one of its
candidates was hard-removed or execution-refuted AND none of its candidates
references a positively resolved identifier. Positive existence support blocks
the suspect flag, including after an execution refutation; it does not undo
hard removal. An operator with multiple surviving provenances is non-suspect
if any supplying revision is non-suspect. Never delete on suspect status.

Preserve Naive's existing per-mechanism-ID timestamp aggregation and all
surviving operators. Source priority is a tie-break, not an extra cost or hard
filter: only among the shared planner's equal-objective candidate plans,
compare their steps' revision priorities lexicographically (non-suspect first,
then newest public timestamp, then stable original index). Apply this additional
tie-break only when suspect/non-suspect alternatives coexist for a relation;
otherwise retain the exact Naive plan order. Do not alter MIP objectives,
confidence, costs or candidate count. This explicit implementation detail is
necessary because frozen Naive does not select one payload per relation.

Execute one shared-planner step and replan, with the same inventory awareness,
action-signature deduplication and resource-error isolation as Naive. A success
with a different expected output, or an interface rejection with satisfied
input/tool/fuel preconditions, refutes the supplying candidate. Missing input,
tool, fuel, depleted resources or indeterminate feedback does not establish
mechanism falsity. A failed action is still blocked exactly as in Naive.
Refuted candidates are removed and their revisions reconsidered. Precondition
checks use only the execution-time inventory and public result/error fields.
No mid-episode probes. Retained suspect candidates can still be planned.

## Boundaries, exclusions and QA

CP-RAG is conflict-triggered reactive mechanism adjudication, without revision
generalization. VB-RAG filters by a temporal window; PF does not. Probe-then-RAG
is a designer-mapping reference, not an autonomous comparator. Do not substitute
the deprecated CP evaluation adapter for the frozen baseline.

Tests must cover probe scores/ties, duplicate payloads, B, fallback, unknown
responses, absent propagation, positive-support exception, revision isolation,
suspect survival, plan ties, execution refutation/resource errors, action budget,
and byte-identical no-conflict action sequences against frozen Naive. Count and
report that identity fraction; any counterexample fails QA, not an exclusion.
No difficult or unsuccessful instance may be silently dropped.

report counts and origin separately. Natural version mentions in required raw
public snippets must not be silently stripped or declared absent. The literal
requested zero-version-string QA fails if such strings occur; record a blocker
rather than claiming compliance or rewriting the rule. Independently require
zero policy access to forbidden files and zero version-conditioned decisions.
Scoring may read gold only after the policy has terminated, outside its process.

Run serial, nice 15, single-threaded native solver, shared server.lock held for
the run, available-memory gate 1.8 GiB with ten-minute polling if needed; do not
touch unrelated processes. Log peak RSS, wall time and zero LLM/currency cost.
Byte replay compares canonical episode/action content excluding seed,
timestamps, run paths and measured wall time, not byte identity of envelopes
with intentionally different seeds. Preserve both raw seeds and report any
