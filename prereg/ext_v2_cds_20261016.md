# W7a EXT-v2 and controlled diagnostic suite preregistration

**Rule registration date:** 2026-10-16 (UTC), before W7a screening, task
selection, pipeline execution, or result inspection.

## Scope and chronology

W7a is a deterministic, zero-LLM-call post-review diagnostic. It reads frozen
truth, conflict, corpus, simulator, planner, Core42, W5, and W6 assets but does
not modify them or any reported main-matrix number. EXT-v2 and CDS remain
separate from Core42 and W6 EXT.

This document is committed in two stages. The first commit freezes every rule
below before screening. A second, pre-method freeze commit will append the
selected families, tasks, packages, cells, input hashes, and generated material
hashes after deterministic setup but before any evaluated EXT-v2 or CDS pipeline
episode. No rule may change in that second commit.

## Behavior-authenticity screen

A mechanism passes if and only if an action sequence executable from the
frozen arena and public initial bundle has an observable result that differs in
at least two of Java 1.16.5, 1.19, and 1.21.11. Observable output is restricted
to produced item identifier and count, feasibility, and the frozen public
error-category whitelist. Recipe IDs, tags, coordinates, and private truth are
not observable evidence.

The deterministic verifier uses these rules:

- Recipe and concrete-grid assertions enumerate every frozen executable
  crafting-grid or furnace terminal action induced by the assertion. The
  oracle obtains the concrete prerequisites separately in each world; the
  identical terminal action is then replayed in all worlds.
- Craftability assertions run the oracle for the asserted goal in all worlds
  and replay every feasible minimum plan. The observable signature is
  feasibility plus final goal identifier/count and public failure category.
- Name assertions execute `check_name` for the registered identifier in all
  worlds. This may establish behavioral authenticity but does not by itself
  make a planner task representable.
- When several witnesses distinguish worlds, choose minimum semantic cost,
  then action count, source version, and canonical action JSON.

An assertion fails if differences are only tag membership outside the arena,
equivalent alternative ingredients, recipe JSON encoding, or another
non-observable representation change. Failure reasons use, in order,
`tag_members_outside_arena`, `equivalent_alternative_ingredient`,
`recipe_json_format_change`, and `other_representational`. The verifier is run
from source truth and simulator state; prior authenticity labels are not read
as decisions.

## Mechanism families and independence

Family assignment is performed before looking at W7a outcomes. Recipe and
craftability assertions for the same subject share a family. The following
feature families override the subject default:

- all `*_spear` items: `feature:spear_family`;
- all `*_harness` items: `feature:harness_family`;
- raw-iron/raw-gold items and their storage blocks:
  `feature:raw_material_introduction`;
- iron/gold ingot furnace routes: `feature:raw_ingot_smelting`;
- wooden tools: `feature:wooden_tool_recipe_family`;
- stone tools: `feature:stone_tool_recipe_family`;
- blue wool and blue carpet: `feature:blue_wool_chain`;
- rename pairs `grass_path/dirt_path`, `grass/short_grass`,
  `scute/turtle_scute`, and `chain/iron_chain`: one family per rename event.

All other candidates use `<kind-family>:<subject>`, where recipe and
craftability both use `item:<subject>` and name assertions use their normalized
rename-event key. Candidates that share the same decisive terminal action,
truth transition, and required predecessor mechanism are merged into the
lexicographically first family key. This last merge is mechanical and its
evidence is written to the screen.

The family, not the assertion or task, is the resampling unit. A family may be
behaviorally real but ineligible for task generation when the frozen pipeline
cannot express its decision action. In particular, `check_name` is observable
but is not a goal-producing operator in the frozen planner, so name-only
families are marked `planning_interface_unrepresentable` rather than forcing a
task.

## Corpus coverage and diagnostic packages

T1/T2/T3 existence is computed from exact conflict IDs and the frozen formal-P1
claims/coverage files. Coverage is `two_sided` when both temporal sides exist,
`one_sided` when exactly one exists, and `missing` otherwise. Coverage never
changes authenticity or CDS eligibility; only `two_sided` and `one_sided`
families enter EXT-v2 Web cells.

For each task candidate, the diagnostic package is the multiset deficit needed
for the chosen distinguishing terminal action after the public initial bundle.
It may contain intermediate ingredients, tool, or fuel but never the goal. It
is identical across worlds, methods, and cells and is explicitly recorded.
Candidates requiring no supplement receive an empty package.

## Representative tasks

For every behaviorally real, planner-representable family, candidates are
ranked by: coverage (`two_sided`, `one_sided`, `missing`), maximum finite oracle
cost, action count, mechanism ID, and goal ID. Select one representative. Select
a second only when it has a different subject and a different three-world
truth-transition vector. Thus each family contributes one or two tasks.

Each selected task must:

1. contain one family as its sole decisive changed mechanism;
2. have a fixed goal and package in all worlds;
3. have a validated oracle outcome and cost in all three worlds;
4. have a pair of worlds in which the family changes feasibility or route; and
5. have preferred maximum finite oracle cost at most six.

The cost-six criterion is a preference, not an authenticity exception. A
candidate above six is retained only if its family has no valid shorter
representative, with the reason recorded. A task whose oracle path is decided
by another changed family is rejected. The target is at least 12 independent
families; if fewer qualify, the actual count is reported without changing any
rule.

Every unordered world pair with a different family outcome is a comparison
pair. Both directions are used by CDS. EXT-v2 Web uses exactly five cells per
Web-eligible task: matched T1/1.16.5, matched T2/1.19, matched T3/1.21.11,
mismatched T1/1.21.11, and mismatched T3/1.16.5.

## EXT-v2 pipeline run and statistics

The executable rows are `parametric`, `probe_then_parametric`, `naive_rag`,
`majority_rag`, `truthfinder_rag`, `verify_all`, `arbiter_shell_naive`,
`arbiter`, `oracle`, and `probe_then_rag`. Reading mode is `all_public`; seed is
`20261016`; no LLM is called.

Per family and method, report SR, feasible-only SR, overconservatism, execution
failure, family-specific plan acceptance, family-specific stale query/action
exposure, semantic action count, semantic cost, and search calls. Mismatch
effects subtract the execution-world matched cell from each corresponding
mismatch cell, aggregate tasks within a family first, and then average families.
Percentile 95% intervals use 10,000 family bootstrap samples with NumPy seed
`20261016`. Families, tasks, cells, metrics, or interval rules are never removed
after observing results.

## CDS materials

For each selected task and each directed comparison-world pair, generate five
agent-visible knowledge conditions in one canonical JSON file:

- `K`: all target-world-correct mechanisms needed by the oracle path, including
  the focal family;
- `K+S`: K plus the focal stale assertion(s) true in the comparison world;
- `S`: correct non-focal knowledge, with target-world focal assertions removed
  and comparison-world stale focal assertions retained;
- `empty`: correct non-focal knowledge with every focal assertion removed; and
- `K+N`: K plus unrelated true neutral facts equal to K+S's stale additions in
  count and Unicode-codepoint text length.

Every visible entry has only `mechanism fact`, `source`, and `timestamp`.
Entries are deterministically shuffled using SHA-256 of seed, instance ID, and
condition. Timestamps are the registered corpus eras T1, T2, and T3; stale facts
use an era in which they are true. Neutral facts are selected
lexicographically from executable mechanisms unrelated to every task target,
use the stale fact's timestamp distribution, and are right-padded with spaces
only to match length. They remain true in the target world.

Each instance also has a boundary question containing every focal candidate
assertion in shuffled order. Truth labels are written to a separate evaluator
file and never appear in agent-visible material. Materials are injected as an
equivalent in-memory claim cache; the frozen search indexes and claim caches are
not edited.

## CDS pipeline run and boundary score

All ten executable pipeline rows run on all five CDS conditions for every
directed comparison instance, with seed `20261016` and zero LLM calls. The same
outcome, exposure, and cost metrics as EXT-v2 are reported.

Boundary decisions are read from each method's frozen aggregation/disposition
rule over the injected claims. Posterior probability at least 0.5 means true,
below 0.5 means false, and absent evidence is abstention and scored incorrect.
Probe rows additionally use a completed focal probe's public observation;
oracle uses target truth; parametric rows use only their frozen prior. Accuracy
is the number of exactly correct candidate labels divided by all focal
candidate labels, with abstentions also reported separately. The scoring rule
cannot be changed after outcomes are known.
